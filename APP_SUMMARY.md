# INC-IO-Docs App Summary

This document provides a high-level overview of the INC-IO-Docs application, designed to give agents and developers context on its purpose, architecture, and technology stack without requiring direct access to the codebase.

## 1. What the App Does

INC-IO-Docs is a **Schema-Driven Document Management App** and rules engine. It acts as a core system that validates payloads, resolves identities, and orchestrates activities around structured documents.

**Key Capabilities:**
*   **Schema-Driven:** Operates based on `DocumentType` JSON schemas loaded from a runtime directory. These schemas dictate the shape of data payloads, presentation UI (`FormSchema`), and fields.
*   **Document Management:** Manages `Document` instances—validated, immutable records that perfectly satisfy a `DocumentType`. These records contain references to file locations (e.g., on Google Drive) rather than embedding binary files.
*   **Activity Orchestration:** The core domain generates declarative instructions (`Activity` objects) that are executed by driven adapters (e.g., writing to Google Drive, communicating with external APIs).
*   **Workspace Integration:** The primary user interface is a Google Workspace Add-on, allowing users to interact with the document management system directly from Google Workspace.

## 2. Architecture

The application strictly follows a **Hybrid Hexagonal Architecture** (Ports and Adapters), balancing feature locality with infrastructure leverage.

### Directory Structure & Layers

*   **`src/features/` (High Locality):** Contains self-contained feature slices (e.g., `document`, `document-space`, `workspace`). Each feature directory includes:
    *   `domain.ts`: Core business logic and type definitions. Completely isolated from external dependencies (except Typebox).
    *   `ports.ts`: Interfaces defining explicit boundaries (driving and driven ports).
    *   `adapters/`: Implementations that bridge the feature's ports to the outside world.
*   **`src/infrastructure/` (High Leverage):** Contains pure, domain-agnostic modules that handle external systems (e.g., `drive/`, `workspace-addon/`, `http/`). These modules **never** import from `features/`.
*   **`src/app/` (Wiring Layer):** The only place where infrastructure modules are injected into feature adapters.

### Rules Engine & State Mutation
*   **Payload vs Context:** The domain operates purely on serializable `payloads`. Ephemeral secure credentials and environment resources are passed via an `ExecutionContext` side-channel, strictly separated from domain data.
*   **Activities:** Mutations and side-effects are modeled as `Activity` instructions generated by the domain and passed out to driven adapters for execution.

## 3. Tech Stack

*   **Language:** TypeScript
*   **Validation & Types:** Typebox (used extensively for JSON schema validation, runtime validation, and static type inference)
*   **API Framework:** Fastify (with Typebox provider)
*   **Deployment:** Google Cloud Run
*   **Testing:** Vitest (co-located unit tests in `src/`, E2E/integration tests in `test/`)
*   **Primary Interfaces:**
    *   Google Workspace Add-on (Driving Port)
    *   Fastify REST API (Driving Port)
*   **Storage & Integrations:**
    *   Google Drive API (Serializes and stores document metadata as JSON)
    *   App Runtime Directory (Reads JSON schemas)
    *   PDF manipulation tools (e.g., `pdf-lib`, `unpdf`)
