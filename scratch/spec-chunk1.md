## Problem Statement

The user needs to establish the foundational Core Engine scaffold for INC-IO (a document management app) utilizing a Hexagonal architecture. This first chunk needs to accept a JSON payload via an HTTP POST endpoint, validate it against a hardcoded schema (`RecordType`), and execute a declarative mock `Activity` using an external adapter.

## Solution

Create a Fastify POST endpoint as the driving adapter that accepts the raw `Record` payload. Implement the Core domain logic that validates the payload and determines the required activities. Finally, dispatch these `Activity` commands across an `ActivityDispatcherPort` to an `ActivityEngine` (a stateless worker adapter) which executes a mock operation (like a console log) to prove the end-to-end flow.

## User Stories

1. As an API client, I want to submit a JSON payload representing a document record, so that it can be processed by the system.
2. As the Core engine, I want to validate the incoming payload against a specific `RecordType` schema, so that I ensure only well-formed data enters the domain.
3. As an API client, I want to receive a 400 error when submitting an invalid payload, so that I know what to fix.
4. As the Core engine, I want to evaluate valid records and yield declarative `Activity` commands, so that side-effects are decoupled from domain logic.
5. As an ActivityEngine, I want to receive `Activity` commands via the `ActivityDispatcherPort` and execute them, so that the required side-effects (like logging) happen outside the Core.

## Implementation Decisions

- **Modules & Architecture**: The core domain represents the `record` feature slice (`src/features/record/`).
  - **Core Domain** (`domain.ts`): Contains Typebox definitions, validation logic, and yields pure `Activity` commands.
  - **Ports** (`ports.ts`): Defines the `ActivityDispatcherPort`.
  - **Driving Adapter** (`adapters/http.ts`): The Fastify POST endpoint.
  - **Driven Adapter** (`adapters/activity-engine.ts`): The stateless worker that executes the mock activities.
  - **Wiring Layer** (`src/app/server.ts`): Connects the HTTP adapter, injects the `ActivityEngine` into the port, and starts the server.
- **Driving Interface**: A single Fastify POST endpoint. It will accept the raw `Record` payload directly at the JSON root, without any metadata envelope.
- **Driven Interface**: A single `ActivityDispatcherPort` using the Command pattern. The Core yields `Activity` objects, which the `ActivityEngine` executes.
- **Domain Definitions**:
  - `RecordType`: The structural definition (Typebox schema) for a class of documents.
  - `Record`: A validated, immutable instance of data that perfectly satisfies a `RecordType`.
  - `Activity`: A declarative instruction generated by the core domain, dispatched across a driven port to be executed by a driven adapter.
- **Validation**: Use Typebox to validate the payload against a single hardcoded `RecordType` schema.

## Testing Decisions

- **Testing Principles**: Only test external behavior across the established seams. Tests should mock the driven port (`ActivityDispatcherPort`) and invoke the driving port (the HTTP endpoint or the Core interface directly) to assert that the correct sequence of activities is yielded.
- **Modules Tested**: Core domain logic and the `ActivityEngine` orchestration logic.
- **Prior Art**: We are establishing the first chunk, so we will set the precedent for unit testing with Vitest co-located in `src/`, with mocks for driven ports.

## Out of Scope

- Dynamic routing or loading of multiple `RecordType` schemas (reserved for Chunk 2).
- Real external integrations like Google Drive (reserved for Chunk 5).
- Handlebars interpolation (reserved for Chunk 3).
- Complex workflow orchestration and event routing based on rules (reserved for Chunk 4).
