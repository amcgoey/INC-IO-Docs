# Bidirectional DocumentFormSchema with Handlebars Field Templates and Unified FormExtractorPort

Structured document form mappings (covering both PDF AcroForm widgets in `application/pdf` files and Google Docs form fields/smart chips in `application/vnd.google-apps.document` files) live in a single top-level `documentFormSchema` block inside each `DocumentType` JSON file—keyed by form field name and expressed strictly using Stage-1 `DocumentField` Handlebars `template` strings (`"{{section}}-{{number}}-{{revision}}"`, `"{{specTag.key}}-{{revision}}"`, `"{{action.name}}"`, `"{{date}}"`) with optional `format: "date"` (`yyMMdd` internally ↔ `yyyy-MM-dd` ISO human-readable form output) and optional `valueMap` overrides—while `documentParseSchema.extractors` includes `{ "source": "form" }` (plus optional `name` and `JsonLogic` `match` predicates) solely to control Pass 2 pipeline precedence (`gmail` → `form` → `drive`).

Defining separate `pdfFormSchema` / `googleDocSchema` blocks, encoding Google-Docs-specific table cell coordinate offsets inside `DocumentFormSchema`, keeping separate `source: "pdfForm"` and `source: "googleDoc"` extractors, duplicating field names across `documentParseSchema` (for Pass 2 reading) and `documentWorkflowConfig` (for future cover-sheet stamping/writing), splitting each field into separate `read` and `write` sub-schemas, or referencing `CalculatedField`s inside `documentFormSchema` ([0016-calculated-fields-isolation-on-document.md](0016-calculated-fields-isolation-on-document.md)) was rejected because PDF AcroForm templates and Google Doc templates represent the exact same domain concept—structured interactive form fields inside a Drive document—differing only in infrastructure wire format, whereas baking table row/column offsets into `DocumentFormSchema` would leak Google Docs DOM geometry into PDF schemas, shallow `FormExtractorPort`'s `{ id, mimeType }` interface and `${mimeType}:${id}` request memoization across `DocumentType` switches, fail to express checkbox option tables or standalone `Dropdown` Smart Chips, and collide with intentionally unmapped human fields (`"Reviewed By"`, `"REMARKS"`). Routing both formats behind one deep `FormExtractorPort` (`DriveFormExtractorAdapter` dispatching by resolved `mimeType`) and one Stage-1 Handlebars binding (parsed via `HandlebarsAdapter` per [0003-handlebars-for-injection-not-logic.md](0003-handlebars-for-injection-not-logic.md)) lets `SourceParser` decompose composite field strings into validated `DocumentField`s on read while future `Document` form-writing `Activity` adapters render the exact same template on write. Per [0009-split-manifest-configuration-and-feature-schema-hydration.md](0009-split-manifest-configuration-and-feature-schema-hydration.md), `ParseSchemaRegistryAdapter` hydrates and startup-validates `documentFormSchema` via `RawManifestProviderPort` without coupling `src/features/document/` to `src/features/source-parser/`, and form field defaults remain owned by the PDF or Google Doc template itself rather than hardcoded placeholder strings in JSON.

For `application/vnd.google-apps.document` items, `DriveFormExtractorAdapter` delegates to `GoogleDocsClient.extractDocumentFormFields` (`docs.googleapis.com` `documents.get` with `includeTabsContent: true` and `suggestionsViewMode: 'PREVIEW_WITHOUT_SUGGESTIONS'`, authorized under the existing `https://www.googleapis.com/auth/drive` scope without encapsulating raw `Schema$Document` outside `src/infrastructure/docs/`), extracting 5 deterministic structural widget patterns—Heading + Checkbox Option Tables (`☐` / `☑` `Dropdown` Smart Chips with explicit checkbox glyph fallback, reporting `2+` checked rows or conflicting cross-tab selections in `ambiguousFields` for non-blocking user warning), `2×1` stacked field boxes, `2×N` signature/caption tables (using semantic value-side signals on `Row 0` vs. static non-date/non-numeric captions on `Row 1`, normalizing `DateElement` chips to ISO `YYYY-MM-DD`, and stripping unset `U+E907` Date Placeholder chips), `N×2` key/value tables, and standalone `Dropdown` Smart Chips—rejecting unreadable native checklists (`BULLET_CHECKBOX`), fragile character-offset `NamedRanges`, and non-writable `.docx` `docProps/custom.xml` Variable Smart Chip exports.
