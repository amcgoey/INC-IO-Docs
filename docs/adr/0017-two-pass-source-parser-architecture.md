# Two-Pass SourceParser Architecture, Lazy SourceContext Hydration, and DocumentParseSchema Decomposition

`SourceParser` (`src/features/source-parser/`) is structured as a deep domain feature module invoked by `UiProcessManager` across two distinct driving passes—Pass 1 (`inferRouting`) and Pass 2 (`extractFields`)—backed by isolated `DocumentParseSchema` hydration (`ParseSchemaRegistryAdapter`), two-tier lazy `SourceContext` hydration, strict canonical-only `LookupField` matching (with automatic `LinkedField` derivation), and non-blocking user-facing status degradation.

### Context & Trade-offs

Pre-populating the Google Workspace Add-on filing card from Gmail and Google Drive sources requires resolving both **where** a document belongs (`DocumentSpaceType`, `DocumentSpace`, `DocumentType`) and **what** field values it contains (`Document.data`). A single-pass schema-driven parser with upfront eager `SourceContext` hydration or monolithic schema validation in `src/features/document/` was rejected because:
1. Routing selects *which* `DocumentSpace` collection `UiProcessManager` must load ([0014-ui-process-manager-space-resolution.md](0014-ui-process-manager-space-resolution.md)) and *which* `DocumentType`'s `DocumentParseSchema` applies in the first place.
2. Eagerly downloading Drive PDF buffers or reading Google Docs Variable Smart Chips before knowing whether the active `DocumentType`'s `DocumentParseSchema` needs them would blow Google Workspace Add-on card load budgets.
3. Coupling `DocumentParseSchema` into `src/features/document/` violates feature isolation ([0009-split-manifest-configuration-and-feature-schema-hydration.md](0009-split-manifest-configuration-and-feature-schema-hydration.md)); conversely, passing raw schemas through `UiProcessManager` on every request makes `SourceParser` shallow and skips startup fail-fast validation.
4. Automated extraction heuristics can produce noisy text fragments that must not violate `DocumentField` constraints (`minLength`, `pattern`) or pollute `LookupField`s with unverified custom strings.

### Decision

1. **Two-Pass Driving Interface (`SourceParserPort`)**:
   - **Pass 1 (`inferRouting`)**: Driven by modular, source-specific resolvers (`drive`, `gmail`) and `Manifest` space configuration (`DocumentSpaceTypes` `storageConfig` hierarchy rules, `spaceSchema.defaultDocumentType`, and `configuration.workspace.defaultDocumentSpaceType`) rather than `DocumentType` JSON schemas or hardcoded space/type defaults. Returns best-effort, partial-friendly `{ spaceTypeId?, spaceIdOrName?, documentTypeKey?, statusMessages? }`. `UiProcessManager` runs `inferRouting` on source-reset events (`isResetOrInitialLoad`, `refresh`, `onEmailMessageChange`, `onFileSourceChange` when switching back to `'Email Attachments'` or when a valid Drive URL is present, and `onFormChange` when `SelectFileSource === 'Google Drive URL'` and `InputDriveURL` transitions to a valid Drive URL) before finalizing the active `DocumentSpaceType`, pre-validates any inferred `spaceIdOrName` against the loaded `DocumentSpace` collection (leaving the space field blank if unmatched), and resolves `documentTypeKey` against `spaceSchema.defaultDocumentType` / `allowedDocumentTypes`.
   - **Pass 2 (`extractFields`)**: Driven by the resolved `DocumentType`'s `DocumentParseSchema` (looked up internally by `documentTypeKey` via `ParseSchemaRegistryPort`). Runs on both source-reset events and manual type-switch events (`onSpaceTypeChange`, `onDocumentTypeChange`), populating only fields not already edited by the user for that `DocumentType`. After merging extracted fields into `formData`, `UiProcessManager` invokes `formEvaluator.evaluate` so `showIf` and `computeValue` rules immediately reflect pre-populated values.
2. **Isolated `DocumentParseSchema` Decomposition, Two-Level Ordered Envelope & Startup Validation**:
   - **Manifest Decomposition (`ParseSchemaRegistryAdapter`)**: `documentParseSchema` is an optional top-level block in each `DocumentType` JSON file. `DocumentTypeSchema` in `src/features/document/domain.ts` stays completely untouched (`Value.Clean` strips unknown blocks). `ParseSchemaRegistryAdapter` in `src/features/source-parser/adapters/` consumes `RawManifestProviderPort`, hydrating `DocumentParseSchema` alongside a minimal local projection of `DocumentSchema` (`ParseTargetDocumentSchema`: `fields` with `key`, `type`, `minLength`, `pattern`, `options`, `linkedField`; `calculatedFields` keys; and static `options` tuples). Its `initialize()` method is invoked during `createApp().initialize()` for fail-fast startup validation.
   - **Two-Level Ordered Envelope**: `DocumentParseSchema` consists of an ordered `extractors: SourceExtractorRule[]` array (discriminated on `source: 'gmail' | 'drive' | 'pdfForm' | 'googleDoc'`, with optional `name`, optional `match` filter, and `fields: Record<fieldKey, FieldRule | FieldRule[]>`) plus an optional `fallback` descriptor (`FallbackExtractorRule`). Multiple extractors may share a `source` (e.g., Procore, Autodesk Build, and Generic `gmail` sub-extractors).
   - **Static Cross-Schema Validation**: All four extractor types (`gmail`, `drive`, `pdfForm` AcroForm field mappings, and `googleDoc` Variable Smart Chip mappings, authored by inspecting example files at spec time) declare target `DocumentField` keys statically in `extractor.fields`. Startup validation fails fast if any targeted key in `extractors` or `fallback` is missing from `documentSchema.fields`, targets a `CalculatedField`, or targets a `LinkedField` directly.
3. **Two-Tier `SourceContext` Hydration & Multi-Item Ordering**:
   - **Tier 1 (Base Envelope)**: Hydrated upfront with enriched `GmailMessageDetails` (`subject`, `from`, `to`, `cc`, `date`, `plainTextBody`, `htmlBody`, `attachments`), parsed Google Drive URL targets (in Gmail mode), optional `candidateSpaces` (loaded for the default `DocumentSpaceType` on Gmail card render, plus secondary collections such as `proposals` only when proposal/opportunity markers appear in the email), and an ordered `items` array of selected files/folders (where single-file extractors evaluate against the first matching selected item in order).
   - **Tier 2 (Lazy Driven Content Ports)**: Expensive operations—Drive folder ancestry (`DriveSourceContextPort`), PDF AcroForm extraction (`PdfFormExtractorPort`), Google Doc Variable Smart Chip extraction (`DocVariableExtractorPort`), and dynamic lookup option fetching (`CanonicalOptionsProviderPort`)—sit behind driven ports and execute on demand (cached per request) only when required by Pass 1 or an active extractor in Pass 2 whose target fields are not yet all populated.
4. **Candidate Validation, Canonical-Only `LookupField`s & Automatic `LinkedField` Derivation**:
   - **Two-Level First-Valid-Wins Evaluation**: `SourceParser` walks `documentParseSchema.extractors` in order, skipping any extractor whose source/match is not satisfied or whose target `fields` are already all populated. For each unpopulated `fieldKey` in `extractor.fields`, `SourceParser` evaluates its single rule or ordered rule array in sequence until a candidate satisfies the target `DocumentField`'s `minLength`, `pattern`, and `LookupField` constraints; non-conforming candidates are discarded so evaluation falls through to the next rule/extractor.
   - **Canonical-Only `LookupField` Matching & `LinkedField` Derivation**: For any `LookupField` (static `documentSchema.options` or dynamic `dynamicConfig` resolved via `CanonicalOptionsProviderPort` when `spaceId` is known), `SourceParser` matches extracted candidates strictly against canonical options (`key` or case-insensitive `name`), never pre-populating custom values even when `allowUserInput: true`. Whenever a `LookupField` matches a canonical option tuple, `SourceParser` automatically populates any dependent sibling `LinkedField` (`linkedField.sourceField === field.key`) from `matchedTuple[linkedField.sourceProperty]`.
5. **Pure Deterministic Evaluators + Pluggable Fallback & Non-Blocking Notices**:
   - Deterministic text/metadata/regex/date evaluators live as pure functions in `src/features/source-parser/domain.ts`, while future AI extraction plugs into an optional driven `FallbackFieldExtractorPort`.
   - Extractor or I/O failures never block card rendering; `SourceParser` catches errors at the extractor seam, leaves affected fields unpopulated, and returns clear user-facing notices via `statusMessages` stating what could not be auto-populated and that the user can proceed manually.
