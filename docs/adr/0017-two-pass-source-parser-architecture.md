# Two-Pass SourceParser Architecture, Lazy SourceContext Hydration, and DocumentParseSchema Decomposition

`SourceParser` (`src/features/source-parser/`) is structured as a deep domain feature module invoked by `UiProcessManager` across two distinct driving passes—Pass 1 (`inferRouting`) and Pass 2 (`extractFields`)—backed by isolated `DocumentParseSchema` and 3-tier `aliases` hydration (`ParseSchemaRegistryAdapter` + `stripOptionAliases`), two-tier lazy `SourceContext` hydration, `json-logic-js` condition predicates (`PredicateEvaluatorPort`), opt-in canonical `LookupField` entity resolution (with automatic `LinkedField` derivation), and non-blocking user-facing status degradation.

### Context & Trade-offs

Pre-populating the Google Workspace Add-on filing card from Gmail and Google Drive sources requires resolving both **where** a document belongs (`DocumentSpaceType`, `DocumentSpace`, `DocumentType`) and **what** field values it contains (`Document.data`). A single-pass schema-driven parser with upfront eager `SourceContext` hydration, ambient text-alias scanning across all `LookupField`s, or monolithic schema validation in `src/features/document/` was rejected because:
1. Routing selects *which* `DocumentSpace` collection `UiProcessManager` must load ([0014-ui-process-manager-space-resolution.md](0014-ui-process-manager-space-resolution.md)) and *which* `DocumentType`'s `DocumentParseSchema` applies in the first place.
2. Eagerly downloading Drive PDF buffers or reading Google Docs form fields before knowing whether the active `DocumentType`'s `DocumentParseSchema` needs them would blow Google Workspace Add-on card load budgets.
3. Coupling `DocumentParseSchema` or ingestion `aliases` into `src/features/document/` runtime models violates feature isolation ([0009-split-manifest-configuration-and-feature-schema-hydration.md](0009-split-manifest-configuration-and-feature-schema-hydration.md)) and leaks scraping dictionaries into `Document.data` tuple enrichment; conversely, forcing human or spreadsheet authors to maintain option aliases far away from option tables hurts locality.
4. Ambient substring scanning of option display names causes severe false positives on categorical enums (e.g., matching `"Received"` or `"Open"` in ordinary email prose), whereas automated extraction heuristics can also produce noisy text fragments that must never violate `DocumentField` constraints (`minLength`, `pattern`) or pollute `LookupField`s with unverified custom strings.

### Decision

1. **Two-Pass Driving Interface (`SourceParserPort`)**:
   - **Pass 1 (`inferRouting`)**: Driven by modular, source-specific resolvers (`drive`, `gmail`) and `Manifest` space configuration (`DocumentSpaceTypes` `storageConfig` hierarchy rules, `spaceSchema.defaultDocumentType`, and `configuration.workspace.defaultDocumentSpaceType`) rather than `DocumentType` JSON schemas or hardcoded space/type defaults. Returns best-effort, partial-friendly `{ spaceTypeId?, spaceIdOrName?, documentTypeKey?, statusMessages? }`. `UiProcessManager` runs `inferRouting` on source-reset events (`isResetOrInitialLoad`, `refresh`, `onEmailMessageChange`, `onFileSourceChange` when switching back to `'Email Attachments'` or when a valid Drive URL is present, and `onFormChange` when `SelectFileSource === 'Google Drive URL'` and `InputDriveURL` transitions to a valid Drive URL) before finalizing the active `DocumentSpaceType`, pre-validates any inferred `spaceIdOrName` against the loaded `DocumentSpace` collection (leaving the space field blank if unmatched), and resolves `documentTypeKey` against `spaceSchema.defaultDocumentType` / `allowedDocumentTypes`.
   - **Pass 2 (`extractFields`)**: Driven by the resolved `DocumentType`'s `DocumentParseSchema` (looked up internally by `documentTypeKey` via `ParseSchemaRegistryPort`). Runs on both source-reset events (purging prior unsuffixed and docType-suffixed data keys before merging) and manual type-switch events (`onSpaceTypeChange`, `onDocumentTypeChange`, preserving inactive `_${otherDocType}` suffixed keys and non-empty active-type user edits while populating blank fields). After merging extracted fields into `formData`, `UiProcessManager` invokes `formEvaluator.evaluate` across all render paths so `defaultValue`, `showIf`, and `computeValue` rules immediately reflect pre-populated values.
2. **Isolated `DocumentParseSchema` & `aliases` Decomposition, Two-Level Ordered Envelope & Startup Validation**:
   - **Hydration-Time Decomposition (`ParseSchemaRegistryAdapter` & `stripOptionAliases`)**: `documentParseSchema` and `documentFormSchema` ([0018-bidirectional-document-form-schema.md](0018-bidirectional-document-form-schema.md)) are optional top-level blocks in each `DocumentType` JSON file, and option tuples may carry optional authoring-local `aliases?: string[]` alongside shared `Manifest` `AliasDictionary` files (`manifest.aliases`). `DocumentSchemaRegistryAdapter` explicitly strips `aliases` from hydrated `DocumentSchema` option tuples (`stripOptionAliases`) so `Document.data` and `SchemaDrivenUi` remain purely canonical. `ParseSchemaRegistryAdapter` in `src/features/source-parser/adapters/` (encapsulated inside `src/app/source-parser.wiring.ts`) consumes `RawManifestProviderPort`, hydrating `DocumentParseSchema`, `DocumentFormSchema`, `ParseTargetDocumentSchema` (retaining local option `aliases`), and shared `AliasDictionary` mappings, with `initialize()` invoked during `createApp().initialize()` for fail-fast startup validation.
   - **Two-Level Ordered Envelope & Orthogonal `FieldRule`s**: `DocumentParseSchema` consists of an ordered `extractors: SourceExtractorRule[]` array (discriminated on `source: 'gmail' | 'form' | 'drive'`, with optional `name`, optional `json-logic-js` `match` filter, and per-field `FieldRule | FieldRule[]` maps on `gmail`/`drive` or shared bidirectional Handlebars bindings in `documentFormSchema` for `form`) plus an optional `fallback` descriptor (`FallbackExtractorRule`). In `DocumentType` schemas, `source: 'gmail'` precedes `source: 'form'` and `source: 'drive'` (`gmail` → `form` → `drive`) so higher-signal email context wins first in Gmail `Google Drive URL` mode, structured PDF AcroForm and Google Docs form fields beat Drive timestamps and filename heuristics, and `drive` fills remaining blank fields. Boolean conditions (`extractor.match` and `FieldRule.when`) reuse standard `json-logic-js` injected via `PredicateEvaluatorPort`, paired with three orthogonal rule primitives: conditional assignment (`{ when?, set }`), direct/pattern extraction (`{ when?, from, pattern?, flags?, group?, normalize? }`), and opt-in entity resolution (`{ when?, from, pattern?, flags?, group?, normalize?, excludePattern?, lookup: true }`).
   - **Static Cross-Schema Validation**: All three extractor types (`gmail`, `drive`, and `form` via Stage-1 `DocumentField` Handlebars templates in `documentFormSchema`, authored by inspecting example PDF and Google Doc templates at spec time) declare target `DocumentField` keys statically. Startup validation fails fast if any targeted key in `extractors`, `documentFormSchema`, or `fallback` is missing from `documentSchema.fields`, targets a `CalculatedField`, or targets a `LinkedField` directly, if `lookup: true` or `valueMap` targets a non-`LookupField`, if any `.prop` path or multi-token field combination in `documentFormSchema` is invalid, if any `normalize` mode or regex `pattern`/`excludePattern` is invalid, or if normalized `aliases` or `valueMap` entries collide; `AppManifestProvider` likewise validates optional `configuration.workspace.timeZone` (read lazily by `SourceParser` via `SourceParserConfigPort` for UTC ISO timestamp formatting) per [0009-split-manifest-configuration-and-feature-schema-hydration.md](0009-split-manifest-configuration-and-feature-schema-hydration.md).
3. **Two-Tier `SourceContext` Hydration, Correlated Multi-Item Binding & Request Memoization**:
   - **Tier 1 (Base Envelope)**: Hydrated upfront with enriched `GmailMessageDetails` (`subject`, `from`, `to`, `cc`, `date`, `labels` resolved via per-token TTL-cached `gmail.users.labels.list` with raw `labelIds` fallback, `plainTextBody`, `htmlBody`, `attachments`), parsed Google Drive URL targets (in Gmail mode), optional `candidateSpaces` (loaded for the default `DocumentSpaceType` on Gmail card render, plus secondary collections such as `proposals` when proposal/opportunity markers appear in non-system `labels`, `subject`, or body), and an ordered `items` array of selected files/folders. Single-file (`form`, and `drive` evaluated in declared field order so identifying submittal fields bind `boundDriveItemId` ahead of universal timestamp fallbacks) and `attachmentName` extractors bind to the first matching item/attachment per extractor so fields never splice across distinct files.
   - **Tier 2 (Lazy Driven Content Ports)**: Expensive operations—Drive folder ancestry and item timestamps (`DriveSourceContextPort`, memoizing in-flight and rejected promises per request), structured PDF AcroForm and Google Docs form field extraction (`FormExtractorPort`, backed by `DriveFormExtractorAdapter` dispatching by resolved `mimeType`), and dynamic lookup option fetching (`CanonicalOptionsProviderPort`, sharing a per-request memoized `LookupOptionsPort` with `SchemaDrivenUi`, see [0023-lookup-options-feature-and-document-log-option-tables.md](0023-lookup-options-feature-and-document-log-option-tables.md))—sit behind driven ports and execute on demand (cached per request) only when required by Pass 1 or an active extractor in Pass 2 whose target fields are not yet all populated.
4. **Candidate Validation, Categorical Rules vs. Opt-In 3-Tier `LookupField` Resolution & Automatic `LinkedField` Derivation**:
   - **Two-Level First-Valid-Wins Evaluation**: `SourceParser` walks `documentParseSchema.extractors` in order, skipping any extractor whose source/match is not satisfied or whose target `fields` are already all populated. For each unpopulated `fieldKey` in `extractor.fields`, `SourceParser` evaluates its single rule or ordered rule array in sequence until a candidate satisfies the target `DocumentField`'s `minLength`, `pattern`, and `LookupField` constraints; non-conforming candidates are discarded so evaluation falls through to the next rule/extractor.
   - **Categorical Conditions vs. Opt-In 3-Tier `LookupField` Alias Shadowing & `LinkedField` Derivation**: Categorical `LookupField`s (`action`, `direction`, `status`) populate via deterministic `{ when, set }` metadata rules (verifying canonical option membership without ambient prose scanning). Entity `LookupField`s (`contact`, `vendor`, `specTag`) explicitly opt into `lookup: true` against static `documentSchema.options` or dynamic `CanonicalOptionsProviderPort` options (when `spaceId` is known), evaluating **Tier 1** (`DocumentType` local option `aliases`, plus canonical `key`/`name`) → **Tier 2** (dynamic `DocumentLog` `_Config` `aliasesColumn` option `aliases`) → **Tier 3** (shared `Manifest` `AliasDictionary` keyed by trimmed, case-insensitive canonical key). Matching checks `@domain`/email first, exact `key`/`name`/`aliases` second, and escaped delimiter-bounded containment third across Tier 1 → Tier 2 → Tier 3 per step (halting immediately on ambiguity and emitting only canonical option keys, even when `allowUserInput: true`). Whenever a `LookupField` resolves to a canonical option tuple, `SourceParser` emits `String(matchedTuple[field.options.key])` and automatically populates any unedited sibling `LinkedField` (`linkedField.sourceField === field.key`) from `matchedTuple[linkedField.sourceProperty]`.
     - **Per-Token Shadowing & Additive Tier 3 Retention**: `resolveCanonicalOptionFromCandidate` deduplicates alias strings across tiers via a trimmed, case-insensitive `seenNormalizedAliases` token set rather than discarding an option's Tier 3 mapping when Tier 2 is present. Tier 2 tokens are hydrated from `_Config` `Aliases` cells parsed as RFC 4180 CSV—preserving comma-containing quoted tokens (such as `"Pavarini, ""NYC"" Group"`) and `""`-escaped quotes—and concatenated case-insensitively across duplicate-key rows (`DocumentLogService`, see [0023-lookup-options-feature-and-document-log-option-tables.md](0023-lookup-options-feature-and-document-log-option-tables.md)). A Tier 2 token claims and shadows only that colliding token in Tier 3 (even across different canonical keys, e.g., overriding a shared `@domain`), while all non-colliding Tier 3 domain and phrase tokens for both customized and uncustomized keys remain active additively (and Tier 3 supplies full fallback when `_Config` omits `Aliases` or leaves a cell blank).
5. **Pure Deterministic Evaluators + Pluggable Fallback & Non-Blocking Notices**:
   - Deterministic text/metadata/regex/date/lookup evaluators live in `src/features/source-parser/domain.ts` (with `json-logic-js` injected via `PredicateEvaluatorPort`), while future AI extraction plugs into an optional driven `FallbackFieldExtractorPort`.
   - Extractor or I/O failures never block card rendering; `SourceParser` catches errors at the extractor seam, leaves affected fields unpopulated, and returns clear, deduplicated user-facing notices via `statusMessages` stating what could not be auto-populated and that the user can proceed manually (distinguishing password-protected PDFs, unparseable form documents, and ambiguous multi-selected form options from Drive/Docs transport errors), with `UiProcessManager` suppressing redundant Pass 2 Drive/Docs transport notices when Pass 1 already emitted a Drive hierarchy warning in the same request.
